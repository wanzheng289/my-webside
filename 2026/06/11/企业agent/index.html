Project Dossier

基于 RAG 的企业客服运营 Multi-Tool Agent 平台

2026-06-11 projects #RAG #Agent #Python #FastAPI #LangGraph #MCP #Neo4j #Milvus

项目概述

这个项目是一个面向企业客服与运营场景的 Multi-Tool Agent 平台。我把它包装成一个虚拟 SaaS 公司 Deedly CloudOps 的内部客服运营工作台：客服、客户成功或 on-call 工程师可以直接输入自然语言问题，系统会根据问题自动调用客户画像、历史工单、企业知识库 RAG、企业知识图谱和评测链路，最后生成带证据来源的答复。

我最初设计这个项目时，并不想只做一个“能聊天的 RAG Demo”。普通 RAG 项目通常只能回答“文档里有什么”，但真实企业客服/运营场景往往需要同时判断客户是谁、历史上发生过什么、当前问题影响哪些产品和团队、是否有相似工单、文档证据是否可靠、下一步应该转给谁处理。因此这个项目的重点不是单一问答能力，而是把企业客服场景里的多种上下文组织进一个可观测、可迁移、可评估的 Agent 工作流。

项目目前支持三类核心问题：第一类是客服回复生成，例如“客户生产环境无法登录 SSO，请判断优先级并给出下一步建议”；第二类是企业知识问答，例如“总结某个部署 runbook 的注意事项，并说明涉及哪些团队或服务”；第三类是图谱增强问答，例如“某个客户和 SSO 产品有什么关系，历史上出现过什么问题”。在前端页面中，用户能看到 Agent 的最终回答，也能看到它调用了哪些工具、检索到了哪些 RAG 来源、命中了哪些客户记忆、查询到了哪些 KG 路径，以及本轮回答的评测信号。

为什么选择企业客服/运营场景

我在项目选题时比较过医疗、企业、游戏/运营/客服等方向。医疗数据集相对容易找到，而且知识图谱也有天然空间，但如果没有真实业务流程，很容易变成单纯的医疗问答；游戏或运营场景也有 Agent 想象空间，但如果缺少领域数据，项目会显得不够可信。最后我选择企业客服/运营，是因为这个场景同时具备 RAG、Memory、Tool Calling、Knowledge Graph 和评测链路的合理需求。

在企业客服里，RAG 可以处理知识库、runbook、产品文档和内部 SOP；Memory 可以记录客户偏好、历史问题、沟通风格和待跟进事项；知识图谱可以表达客户、产品、工单、团队、服务、文档之间的关系；Tool Calling 可以把这些能力组合成真实工作流；Eval Harness 则可以评估检索、引用、工具调用和回答质量。这个组合比单纯做“文档问答”更接近真实企业里的 Agent 应用。

为了让公开数据看起来不像一堆互不相关的文件，我设计了 Deedly CloudOps Demo Workspace 这个虚拟公司设定。公开数据集被映射成企业知识库、客户、产品、工单、团队、服务和图谱关系。例如 SSO 被设定为身份认证产品，perf-canary 被设定为部署/回滚相关服务，CustQRWQE 被设定为一个曾经出现过 SSO 访问问题的客户。这样演示时用户看到的是一个完整业务环境，而不是孤立的数据样本。

技术架构

项目后端基于 FastAPI 构建，核心模块包括 Agent Workflow、RAG、Memory、Knowledge Graph、Tool Layer、Eval Harness 和 MCP-like Servers。前端是一个轻量的聊天工作台，风格参考企业内部工具和 evidence workspace：左侧是对话区和工具轨迹，右侧是 Agent Evidence Brief，用于展示 RAG Sources、KG Paths、Memory Hits 和 Eval Report。

整体链路可以概括为：

RAG 部分使用 Milvus 存储向量，PostgreSQL 存储 parent chunks 和结构化记录，支持文档分块、向量检索、rerank 预留接口、citation 构建和来源展示。Memory 部分包括客户画像、历史工单、长期记忆和会话记忆，当前 Demo 通过 JSONL/结构化样本实现最小闭环，并预留迁移到 PostgreSQL、Redis 和 Milvus 的路径。知识图谱部分参考了原有 RAGQnASystem 中的实体抽取、关系构建和 Neo4j 查询思路，但不再保留医疗插件，而是迁移到企业知识场景，用企业实体和关系建模客户运营问题。

项目中还抽象了 MCP-like server 层，包括企业知识库、企业图谱、客户运营、Memory 和 Eval 等服务。这样做的目的不是为了增加概念，而是把稳定工具协议化，让 Agent 调用的工具边界更清晰，也方便后续替换成真正的 MCP Server 或企业内部服务。

证据工作台：集中展示工具调用、RAG Sources、KG Paths、Memory 和 Eval Report

数据与业务建模

项目使用公开数据构建 Demo，但底层设计不绑定任何单一数据集。主要数据来源包括 EnterpriseRAG-Bench、Customer Support Conversations、Doc2Dial 和 MultiDoc2Dial。EnterpriseRAG-Bench 用于构建企业知识库和 RAG 评测集；Customer Support Conversations 用于构造客服历史、工单状态、客户画像和 Memory 场景；Doc2Dial/MultiDoc2Dial 用于补充多轮文档问答评测。

为了让系统能迁移到真实公司，我设计了一个标准企业数据模型。真实企业只需要把内部数据映射到五类 JSONL：

  • documents：企业知识库、runbook、产品文档、SOP、事故复盘。
  • customers：客户画像、行业、使用产品、沟通偏好、风险状态。
  • tickets：历史工单、严重程度、状态、问题类型、解决方案。
  • products_services：产品、服务、运行环境、负责人和依赖关系。
  • relations：客户、工单、产品、服务、团队和文档之间的图谱关系。

这种设计的好处是，Demo 阶段可以使用公开数据集；迁移到真实企业时，只需要替换数据接入和 schema mapping，RAG、Memory、KG、Tool Calling 和 Eval 的主体链路可以保持不变。

核心功能实现

1. 企业知识库 RAG

RAG 模块负责把企业文档转换为可检索知识。文档会先被清洗和分块，写入 PostgreSQL 的 parent chunk 表，同时将向量写入 Milvus。用户提问后，系统会根据 query 检索相关文档片段，并把来源、片段内容和文档元信息返回给 Agent。

在前端展示上，我没有只把 RAG 结果藏在回答里，而是单独做了 RAG Sources 面板。这样面试官或用户可以直接看到回答依据来自哪些文档、source 是什么、doc_id 是什么、片段内容是否真的支持回答。这一点对于企业 Agent 很重要，因为企业客服不只关心“回答是否流畅”，还关心“回答是否可追溯”。

RAG 文档问答场景：回答、引用来源和文档片段同步展示

2. 客户 Memory 与历史工单

客服场景天然需要 Memory。同一个客户可能有固定产品、常见问题、历史工单、沟通偏好和风险等级。项目中，Agent 可以通过工具读取客户画像和历史工单，并把这些信息用于判断优先级和生成客服回复。

例如，当用户输入“客户 CustQRWQE 说生产环境无法登录 SSO，而且很着急”时，Agent 会先识别客户和产品，再查询客户画像、历史工单、相关图谱关系和企业知识库。最终回答不只是泛泛地说“请检查 SSO”，而是会结合客户历史、问题严重程度、可能影响范围和下一步处理建议。

客服回复场景：结合客户画像、历史工单和知识库证据生成处理建议

图谱问答场景：通过 KG Paths 展示客户、产品、工单和团队之间的关系

4. Multi-Tool Agent Workflow

项目不是简单把所有上下文一次性塞给模型，而是设计了 Tool Router 和多条工作流。不同问题会触发不同的工具组合：

  • 客服回复：客户画像 -> 历史工单 -> KG 查询 -> RAG 检索 -> 回复生成。
  • 图谱问答：RAG 检索 -> KG 查询 -> 带图谱路径和引用的答案。
  • 工单优先级：意图识别 -> 情绪判断 -> 优先级规则 -> 相关工单 -> 下一步建议。

这样设计的好处是可解释性更强。用户不仅能看到最后回答，也能看到系统为什么调用这些工具、每个工具返回了什么证据。

5. Eval Harness 与可观测性

为了避免项目停留在“看起来能跑”，我实现了评测链路。Eval Harness 支持 retrieval recall、citation coverage、tool call accuracy、KG query accuracy、memory usefulness、answer faithfulness 和 latency 等指标。前端会展示本轮回答的 Eval Report，例如工具调用数量、引用覆盖率、图谱路径数量和 Memory 命中数量。

这部分是我认为项目比较重要的亮点之一。很多 Agent Demo 只展示最终回答，但真实企业落地需要知道回答是否有证据、工具是否调用正确、记忆是否真的被使用、延迟是否可接受。这个项目把这些信号放在同一个工作台里，便于调试和展示。

前端交互设计

前端最初是三个独立页面：客服回复、图谱问答、工单优先级。后来我把它们合并成一个统一聊天页面，因为真实用户不会在使用前先判断“这个问题属于哪个 workflow”。现在用户只需要在输入框里提问，Agent 会自动路由到对应工具和工作流。

页面采用 Deedly 风格的企业内部工作台设计：主区域显示对话、工具轨迹和回答；右侧 Agent Evidence Brief 固定展示工具调用、RAG Sources、KG Paths、Memory 和 Eval Report。这样的设计让项目更适合演示：面试官可以一眼看到这个系统不只是“调用大模型生成文本”，而是把 Agent 的执行过程和证据链展示出来。

全流程演示：从自然语言提问到工具路由、证据检索、回答生成和评测展示

工程化与可迁移性

这个项目的一个重要目标是“可以被真实企业替换数据后继续使用”。因此我没有把逻辑写死在某一个公开数据集上，而是把企业数据抽象成标准 schema，再通过 data pipeline 进入 RAG、Memory 和 KG 模块。

如果迁移到真实公司，大致流程是：

  1. 导出企业内部文档、客服工单、客户画像、产品服务目录和团队/服务关系。
  2. 转换成项目定义的 documents、customers、tickets、products_services、relations 五类 JSONL。
  3. 运行 schema validator 检查字段、ID、关系和 JSONL 格式。
  4. 重建 RAG 索引、客户 Memory 和企业知识图谱。
  5. 用企业内部高频问题构造 eval set，持续评估检索、引用、工具调用和回答质量。

这也是我希望在简历中强调的地方：项目不是一次性的 Demo，而是围绕真实企业数据接入、知识检索、工作流编排和评测闭环设计的 Agent 平台。

技术栈

后端主要使用 Python、FastAPI、LangChain/LangGraph 风格工作流、PostgreSQL、Milvus、Neo4j-compatible KG、Redis 和 Pydantic。前端使用原生 HTML/CSS/JavaScript 构建轻量工作台。数据处理部分使用 JSONL/CSV pipeline，评测部分实现了独立的 eval harness 和 metrics。模型侧兼容 OpenAI-compatible API，也可以接入国内模型服务；embedding 默认使用本地 BGE-M3 兼容模型。

项目收获

这个项目让我对 Agent 工程化有了更完整的理解。最开始我关注的是 RAG 和知识图谱，但做完整链路后发现，真正决定项目可信度的不是某一个模块，而是模块之间如何协作：RAG 负责事实证据，Memory 负责客户上下文，KG 负责结构化关系，Tool Calling 负责编排，Eval 负责判断系统是否真的做对了。

另一个收获是对“可演示性”的理解。一个项目即使后端功能很多，如果前端无法展示证据链，面试官也很难快速理解亮点。因此我专门把 Tool Trace、RAG Sources、KG Paths、Memory Hits 和 Eval Report 做成可视化区域，让每一次回答都能被检查和解释。

最后，我也意识到真实企业 Agent 的难点往往不是“调用一个模型”，而是如何把数据、权限、工具、评测和迁移流程设计清楚。这个项目虽然是基于公开数据集构建的 Demo，但我尽量把它做成一个接近真实企业落地形态的系统：有数据入口、有检索链路、有记忆、有图谱、有工具调用、有评测，也有可迁移的数据模型。

项目亮点总结

如果用一句话概括：这是一个把企业客服/运营场景中的 RAG、Memory、Knowledge Graph、Tool Calling 和 Eval 统一到同一个可观测工作台中的 Agent 项目。

我认为它最适合作为简历项目展示的亮点有三点：

  • 它不是单纯的文档问答，而是围绕企业客服/运营工作流设计，能结合客户画像、历史工单、企业知识库和图谱关系生成答案。
  • 它有完整的工程结构，包括 FastAPI 后端、RAG 索引、Milvus/PostgreSQL/Neo4j/Redis、MCP-like 工具封装、Eval Harness 和前端 Evidence Workspace。
  • 它考虑了真实企业迁移路径，通过标准数据模型把公开 Demo 和真实企业数据接入连接起来，展示了从原型到落地的工程思考。
